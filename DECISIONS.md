
## Task B decisions (barge-in)

- Root cause of Bug 1: `VoiceSession.onaudioprocess` returned early whenever `isSpeaking()` was true (mic gated while the bot talks), and `onBargeIn` was declared but never called anywhere.
- Mic + pre-roll now stay live during playback. Frames go to `BargeInDetector` (src/shared/barge-in.ts), a pure class so it is unit-testable without DOM/audio.
- Playback threshold = 0.009 * (2.4 - 1.2*sensitivity), i.e. always 1.2x-2.4x the idle threshold so the bot's own voice leaking through the mic does not trigger it. Required continuous speech = 250 ms (sens 0) .. 150 ms (sens 1), default 0.5 -> 200 ms. Gaps up to 80 ms are tolerated.
- ScriptProcessor buffer reduced 4096 -> 1024 (~21 ms at 48 kHz) for latency; frame duration computed from the buffer length. Pre-roll sized in ms (340 ms idle / 400 ms during playback), not in chunks.
- On trigger the session continues as a normal utterance (pre-roll + frames), so the new sentence is transcribed after the usual 750 ms silence; transcription is never sent while the bot speaks without a barge-in. Minimum utterance length raised 2 -> 8 chunks (same ~170 ms as before at the smaller buffer).
- `onBargeIn(info?)` receives performance.now() timestamps; App's shared `handleBargeIn` calls `stopSpeaking('barge-in')`, then `api.stopReply()` (aborts the LLM stream) and logs/pushes `window.__bargeInLatency`.
- New setting `bargeInSensitivity` (0..1, default 0.5), validated, with a slider in Settings > Voice, Focus & Laptop Health.
- Added `allowImportingTsExtensions` to tsconfig.json because voice-engine.ts is imported directly by node tests (strip-types needs an explicit `.ts` specifier); parameter properties avoided in shared TS for the same reason.

## Task C decisions (lip-sync / central stop)
- Root cause of the stuck mouth: main process played TTS with `pw-play` and set `state.isSpeaking` itself, with no way to cancel an in-flight `playSpeech` call. Pressing Stop while a sentence was still being fetched let it start playing afterwards and set `isSpeaking=true` again; nothing sent a final "stopped". The renderer also played the same audio a second time from the returned data URI. The overlay mouth used a boolean plus infinite CSS animations (timer driven) and the mic level, not the output level.
- Decision: main `playSpeech` now only synthesizes (returns a data URI). Playback, stop and level live in one module, `src/renderer/tts-player.ts`, using Web Audio (`AudioBufferSourceNode` -> `AnalyserNode`). `stopSpeaking(reason)` is the only stop path and emits `speech:stop` exactly once per utterance (`UtteranceTracker`).
- Events `start/level/stop` go renderer -> main (`companion:speech-event`) -> all windows (`companion:speech-broadcast`). Main owns `state.isSpeaking`, ignores stale events from superseded utterances and synthesizes a stop if the source window is destroyed mid-speech.
- Overlay/chat mouth is derived from events via `useLipSync` (500 ms watchdog, ignores events unless `voiceCallActive`). The mouth scale is set from the level; the infinite talking CSS animation was removed for the mouth (`is-talking-level`). Head-bob/cheek animations still key off `speaking`, which is watchdog-bound.
- Removed: Google-stream `Audio()` fallback and local Voice Studio helpers (unused, no analyser, could not be stopped centrally). Kept the browser `speechSynthesis` fallback; it emits start/stop but no level, so the mouth stays closed (honest, not faked).
- Sentence N+1 is synthesized while N plays to avoid gaps that would trip the watchdog.
- Reply file naming: the existing `REPORT.md` is the chatbot-fix report, so the voice report is `REPORT-VOICE.md`.

## Task D decisions (wake word)
- Finding for investigation item 4: wake-word-like code DID exist (contrary to the expectation): the overlay's `VoiceSession` ran whenever Live Talk was not on the chat window, sent EVERY detected speech burst to the cloud speech-to-text, and used a regex (`checkWakeIntent`). No toggle, no rate limit, no indicator. That is a privacy problem, so it is replaced.
- "Listen for my name" is a setting, default OFF (`wakeWordEnabled`). With it off and no Live Talk, the overlay does not open the mic at all.
- Local VAD gates everything: only finished speech bursts are considered. In standby only the first 4 s of a burst is sent (`maxClipMs`), with a vocabulary hint built from the name and aliases (`buildWakeHint`), passed through `transcribeAudio(..., hint)` to Whisper's `prompt` / the Gemini instruction. Provider stays in the main process; the hint is sanitised and capped at 300 chars there.
- Rate limit: `WakeGate`: at most one clip per 2 s; on a 429 or error it backs off silently (8 s then doubling to 60 s; 4 s for generic errors) and resets on success. Main now reports `rateLimited` when Groq returns 429.
- Fuzzy matching (`matchWakeWord`): case-insensitive, punctuation-insensitive; edit distance 0 for names up to 3 letters (so "sid"/"sit" never match "said"/"set"/"sir"), 1 for 4-5 letters, 2 for 6+. Two words glued together ("sudo chan") accept at most 1 typo. The name has to appear within the first 4 words, so a sentence that merely mentions "sudo" later does not wake her. This deviates from a pure "edit distance <= 1-2 anywhere" rule on purpose to limit false triggers; "Sit" is in the default aliases per the spec and therefore only matches exactly.
- On a match: the bot greets (`welcome()`), Live Talk opens, and a 30 s `ConversationWindow` starts. Each user utterance and each time she is speaking extends it; when it lapses the wake-opened Live Talk closes. Live Talk the user started by hand is never auto-closed. Anything said after the name in the same breath is sent as the first message.
- Indicator: the overlay shows "Listening for <name>" under the pill, which doubles as the pause button (paused state is per run, not saved).
- Voice lock (speaker pitch check) still applies before a wake is accepted.
- Not done / not verifiable here: real Groq/Gemini round trips with a live mic, false-accept rate in a noisy room, and whether the extra pill fits the small overlay window on every bot size.

## Task E decisions (expressive voice)
- Provider layer: `src/main/tts-provider.ts` (`TtsProvider` interface in `shared/voice-interfaces.ts`, `GeminiTtsProvider`, `GoogleTranslateTtsProvider`, `TtsRouter`). All provider calls and keys stay in the main process; the `playSpeech` IPC still only returns a data URI, so playback/stop/level remain exclusively in `tts-player.ts`.
- Gemini TTS (`gemini-2.5-flash-preview-tts`, `generateContent`, AUDIO modality). Key goes in the `x-goog-api-key` header, never the URL. Raw 24 kHz PCM is wrapped in a WAV header (`pcmToWav`). Gemini is the default engine; with no key, a failure, or a 429 it silently falls back to Google Translate TTS, and Gemini is not retried for 30 s (60 s after a 429).
- Key lookup: the active cloud key if it is Gemini, otherwise `providers.gemini` from the store. The key in this machine's config is not in the `AIza...` format, so the lookup does not rely on that prefix for the stored Gemini entry.
- Emotion: voice-mode system prompt asks for one tag per sentence from [warm] [excited] [calm] [curious] [soft] [happy]. `ChatSession` keeps the raw tagged text in `message.spoken` and shows the stripped `message.text` (including hiding a half-typed `[wa` while streaming). Renderer `speak()` receives `spoken ?? text`, so TTS gets the tags but the UI never shows them. Chosen over stripping in each renderer view because it is one change in main and history sent back to the LLM stays clean.
- Style mapping lives in `shared/speech.ts` (`emotionStyle`); Urdu/Roman Urdu sentences get "pronounce as a native Pakistani Urdu speaker". Roman Urdu is sent as-is, not converted to Urdu script: converting needs an extra LLM call per sentence (latency), and both variants returned valid, non-silent audio in the probe. A person must listen to decide if script is better.
- Speed: Gemini has no speed parameter, so `ttsSpeed` becomes a style hint ("a little faster/slower"). It is not applied to the Google engine.
- Default voice: Kore. Voices selectable in Settings: Kore, Puck, Zephyr, Aoede, Leda, Charon, Fenrir.
- Known cost: Gemini preview TTS took about 4.3-6.8 s per sentence in the probe (free tier), versus well under a second for Google. Sentence prefetch hides some of it, but the first sentence of every reply is delayed. Free tier also rate-limits bursts (429 on rapid parallel calls). The Settings text says so and Google can be selected.

## Follow-up decisions (per-provider keys, Gemini-first STT)
- Finding: the config already had a `providers` map with gemini and groq entries, but `cloudConfig` only wrote `cloud` (the active provider), so saving a Gemini key in Settings would have made Gemini the active chat provider and overwritten the Groq key in `cloud`.
- `cloudConfig` now always writes `providers[<id>]` and only replaces `cloud` when `shouldActivate()` says so: a Gemini key saved while another provider is active is kept for voice only and Settings shows "key saved for voice, chat stays on Groq". `makeActive: true` forces activation. Key lookups for Settings (test/fetch models/save) use the key of the provider being edited instead of the active provider's key (previously a Gemini test with an empty field would have used the Groq key).
- `getProviderKey(id)` (`src/main/index.ts`, logic in `src/main/provider-keys.ts`) feeds Gemini TTS and all STT. On start, the active entry is mirrored into `providers` and plain base64 entries are re-encrypted with `safeStorage` when it is available (on write only; existing `rawKey` still readable). If `safeStorage` is unavailable on this machine they stay base64, as before.
- STT: `src/main/stt.ts` `SttRouter`: Gemini (`gemini-flash-lite-latest`, then `gemini-flash-latest`) with a prompt that asks for Roman Urdu in Latin letters for Urdu speech and English for English, then Groq Whisper (Roman Urdu prompt hint; `language` only when the user explicitly chose en/ur), then OpenAI. 'auto'/'ur-PK' do not force English. 429 backs a route off for 60 s (and is reported as `rateLimited` for the wake gate), other errors for 15 s (not reported as rate limiting). Urdu-script output when Latin was expected is returned with `scriptWarning`, not discarded. Gemini `[none]` means silence and does not spend other providers' quota. Repeated-token and punctuation-only output is rejected.
- Model names: `gemini-2.5-flash` and `gemini-2.5-flash-lite` returned HTTP 404 for the user's key, so the `-latest` aliases are used. `gemini-flash-latest` exceeded the 9 s timeout in a sanity check, so lite goes first.
- Key sent in the `x-goog-api-key` header, never in the URL.

## Startup hang fix
- On this machine `safeStorage.isEncryptionAvailable()` blocks indefinitely (verified with a scratch Electron app: no result after 25 s, process ignored SIGTERM). The key migration added to `start()` called it, so no window was ever created. Startup no longer touches safeStorage; encryption is attempted only when the user saves a key. Legacy base64 keys therefore stay base64 until re-saved.
- Lesson: never run `pkill -f <pattern>` from the agent shell when the pattern appears in the command line itself (it kills the shell).

## Tools decisions (branch `tools`)
- Scope: files (read/write/append/list/search), one-program commands, open link/app, system info. No network tools. Cloud chat path only.
- **Approval is click-only.** `ApprovalManager` has no voice input; the only way to approve is the `companion:tool-approval-reply` IPC, accepted from the chat window. A spoken "haan/yes" is never approval (stated in the card text and the system prompt). Everything that is not an explicit click (60 s timeout, Stop all, no window, unknown id) is a denial.
- Default OFF (`toolsEnabled`). Disabling cancels pending/running actions.
- Path policy resolves symlinks and checks both the typed and the real path against a secrets list; reads outside home need a red card, writes outside home are refused.
- Commands: no shell. Command strings are tokenized without shell semantics and pipes/redirects/chaining are rejected rather than passed through as literals. Child env strips key/token/secret/password variables. `sudo` is allowed only as an "elevated" card.
- Agent loop: OpenAI function calling, non-streamed requests, max 6 tool steps, 4 calls per step, then a final call without tools. If the first request is rejected because of `tools` (400/404/422 mentioning tool/function) the cloud path falls back to plain streaming with the plain prompt. Per-request 60 s timeout; waiting for approval is not counted.
- Modules under `src/main/tools/` avoid runtime relative imports between each other (dependencies are injected) so node's strip-only TypeScript can import them in `tests/tools.check.mjs`; `runtime.ts` is wired to the real policy in `index.ts`.
- Chat window hides on blur (existing behaviour); a new card re-opens and focuses it, and a newly created window pulls pending cards (`companion:tool-approvals`).
- Merge note: touches `local-ai.ts` (prompt + `StreamOptions.tools` + loop hook), `index.ts` (wiring), `preload`, `shared/types.ts`, `shared/validation.ts`, `App.tsx`, `styles.css`. Voice/TTS files are untouched.
